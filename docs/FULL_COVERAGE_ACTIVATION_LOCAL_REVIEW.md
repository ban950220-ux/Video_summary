## What this patch changes

- An ordinary deployment approval may opt in to exactly two additional runtime bindings with `fullCoverageEnabled:true`: plain-text `ENABLE_FULL_COVERAGE="true"` and secret-text `GROQ_FREE_ORG_BINDING_JSON`. Without the opt-in, either binding remains unexpected. Unknown names, wrong types, duplicate names, and a non-`true` flag still fail before and after upload. The existing evidence kind and maximum 24-hour lifetime remain unchanged.
- Both config guards scan the active TOML lines for these two names, including indentation, tabs, inline comments, dotted or quoted keys, and duplicate definitions. They accept only one narrow `ENABLE_FULL_COVERAGE = "true"` assignment in `[vars]`; alternate active spellings fail closed. Comments are ignored. Unicode escapes in active TOML are denied because a quoted key could otherwise hide a protected name.
- The Free record must stay a Worker Secret; it may not be placed in `wrangler.toml`. The normal target guard accepts the flag only as `"true"`. The repository does **not** enable the flag or contain the Free record.
- This is normal protected deployment evidence, not a bypass for `SOURCE_COMMIT_MISMATCH` or the current-state replacement path. A Dashboard settings version created after deployment can change lineage and require a new reviewed deployment path; this patch does not grant one.

## Free key proof limit

`capacityIdentity` hashes the current encrypted D1 credential row (`cipher_version`, IV, ciphertext, `updated_at`) or, when that row is absent, hashes the Worker secret key. It binds a record to the app's current credential representation, **not** to a Groq organization or project. Re-encrypting the same key can change this identity. `fullCoverageKeyBinding` checks the identity, `organizationPlan:"Free"`, `billingDisabled:true`, `confirmedAt`, `expiresAt` no more than 24 hours later, and an ordinary SHA-256 checksum. The checksum detects accidental record changes; it is not a Groq signature or independent billing proof.

The inspected public Groq docs say API keys belong to projects and restrictions are applied at organization/project level. No documented authenticated key-to-organization/billing introspection was found in the inspected API reference. The observed Personal Free console page alone does not prove the existing production credential belongs to that organization. Do not mint a self-asserted Free record from this observation. A pre-existing non-secret audit trail that links the exact current credential to the Free project could be reviewed without showing the key. If none exists, activation remains blocked pending a separately approved credential provenance/rotation procedure; this patch creates no key or provider request.

After this code is deployed, owner Access protects a read-only `GET /api/settings/providers/groq/binding-diagnostic`. It returns `source` (`ENCRYPTED_D1`, `WORKER_SECRET_FALLBACK`, or `NONE`), the app's current `capacityIdentity`, D1 `updatedAt`, and, for a decryptable D1 row, `keyFingerprintSha256`. The Worker temporarily decrypts the D1 key in memory to calculate that fingerprint, but returns no key, IV, or ciphertext and explicitly says `organizationVerified:false`. Treat the fingerprint and identity as private audit data, not public logs or chat content. This diagnostic does not contact Groq or establish billing status.

If the owner later approves a **new dedicated key**, the operator must establish its organization/project and Free/billing-disabled state in the official Groq UI, record the project/key identifier and review time privately, and compute SHA-256 of the newly shown key locally before the value disappears. In the same controlled session, enter the key through the owner-only app route `PUT /api/settings/providers/groq/secret` with same-origin protection. That route encrypts it into D1 `provider_credentials` and returns an `updatedAt`; `resolveProviderKey` prefers this D1 row over any `GROQ_API_KEY` Worker Secret. Re-read the binding diagnostic and require `source=ENCRYPTED_D1`, the expected new `updatedAt`, and an exact match between its `keyFingerprintSha256` and the locally computed fingerprint. Capture the new `capacityIdentity` only after this verification. A Worker Secret replacement alone is insufficient while a D1 row exists. A mismatch, missing fingerprint, changed identity, or uncertain PUT outcome stops activation pending read-only reconciliation; do not resend the PUT blindly. Store the provenance and comparison in a restricted review record without the key value. This is a human-reviewed chain from official project to actual app key, not a provider-signed attestation.
