# Paid response receipt review

This review branch adds migration `0010_paid_summary_receipts.sql`. The migration is not applied to production. Paid execution now checks for this table before reserving or sending a request, so a missing migration blocks new dispatch.

For future calls, the Worker reads at most 256,000 actual response bytes, stores the complete provider JSON body with its SHA-256, request/source/quote hashes and reservation ID, and reads it back before parsing the JSON. It then stores and verifies the provider's model version, finish reason and usage. Headers and API keys are never stored. A broken stream or oversized body gets an `INCOMPLETE` row without a full-response hash or text; it cannot be revalidated. Cloudflare documents a 2,000,000-byte maximum string or row, 100,000-byte SQL statement limit, and 100 bound parameters per query; batch statements retain each query limit. The 256,000-byte response cap is below the row/string limit, and the response is a bound parameter rather than SQL text. See https://developers.cloudflare.com/d1/platform/limits/. Receipt text is private behind owner Access and is never included in status responses. When the owner deletes a job, the deletion tombstone is recorded first; the response text and its hash are then cleared and the receipt is marked `SOURCE_DELETED`. Approval and cost audit rows remain. The receipt insert checks the tombstone in the same SQL statement, so a late provider response cannot recreate private content after deletion.

Validation and save failures retain a safe code and validator version. `POST /api/jobs/:id/paid-summary-revalidate` requires owner Access, same-origin JSON, `reservationId`, and `confirmNoProviderCall: true`. It reads only the server receipt, checks its hash, source and cost ledger scope, requires a complete HTTP 200 `STOP` response, reruns the current strict validator, and conditionally saves the report. It does not call a provider or change approval, trial or settlement rows. A fully stored response can be revalidated even when the later metadata write or readback response failed; the Worker rechecks the full body hash and derives missing metadata from that stored body. If the reservation is still `RESERVED` or `UNCERTAIN`, a saved report is explicitly marked `REVIEW_REQUIRED` for cost reconciliation and the ledger is left unchanged. Duplicate requests cannot save twice. Revalidation has separate version/result fields. The Library only offers the no-call button when a complete receipt exists; a lost historical response has no recovery button.

The 2026-10-12 settled `REPORT_NOT_SAVED` run predates this receipt table. Its response was not stored, so this code cannot recover it or label it successful. No retry, approval reset, settlement reset, production DB write, or deployment is part of this review branch.
