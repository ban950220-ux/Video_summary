# Stored raw-stage number evidence

For a failed Groq raw stage, the owner can open **실패 단계 무호출 진단** in the job detail or request `GET /api/jobs/{jobId}/groq-summary-stage-diagnostic?stage=raw%3A9`. The production site requires a verified Cloudflare Access owner session before this API is reached. The route reads the existing failed operation and the saved source; it does not call a provider or change the database.

When classification is `UNSUPPORTED_NUMBER`, the response includes `numberEvidence`: at most eight mismatches, each with the report field and index, the original numeric token and position, normalized number and unit, a report excerpt, cited evidence IDs, and excerpts of at most eight cited source segments. Numeric token positions come from the original text, so comma and decimal formatting do not shift the excerpt to the beginning. Each source segment states whether the same numeric token is absent or present with a different unit, and shows at most four candidate numeric contexts with original positions. Candidate contexts prioritize the same normalized number, then nearby numerical values; they are not claimed as supporting evidence. If the segment contains no numeric token, the UI says so explicitly. Each excerpt is at most 240 UTF-16 characters and reports its original length, starting offset, and truncation. Returned numeric strings are limited to 64 UTF-16 characters, with original lengths and individual truncation flags; the internal validator still uses the full strings. IDs are capped at 16 per mismatch. The complete JSON diagnostic is limited to 32 KiB and has a `responseTruncated` flag if any detail was shortened or dropped. The UI places every excerpt in `textContent` and keeps the failed stage blocked.

This is a comparison aid, not a finding that the model fabricated a number. The existing validator still compares number and unit tokens against the cited source IDs without conversion of equivalent expressions or units. The diagnostic does not relax that validator, approve a failed stage, recover a receipt, or start another generation. `responseCompleteVerified` and `providerReceiptVerified` remain false when the stored evidence cannot prove them.
