## 1. 목표

사용자가 PC나 휴대폰(PWA)에서 **YouTube URL 하나만 넣으면**:

1. 자막 또는 전사문을 자동으로 확보하고
2. 한국어 **핵심 요약**과 **타임스탬프 챕터**를 만들어
3. 라이브러리에 저장하고, 다시 열기·검색·삭제·내보내기를 할 수 있게 한다.

사람이 단계마다 "견적 승인" 버튼을 누르지 않아도 끝까지 자동으로 진행되는 것이 핵심이다.

## 2. 범위

### 1차 범위 (이번 개발)
- URL 입력 → 자막/전사 확보 → 요약·챕터 생성 → 저장 (자동 진행, 진행률 표시)
- 수동 입력 대체 경로: SRT/VTT/TXT 업로드 (기존 파서 재사용)
- 라이브러리: 목록, 제목/영상 ID 검색, 다시 열기, 삭제, Markdown/TXT 내보내기
- 설정: 제공자 API 키 등록·교체·삭제 (기존 암호화 금고 재사용), 무료 사용량 표시
- PWA: manifest, 192/512/maskable 아이콘, 서비스 워커(등록만, API 캐시 없음)
- map-bot 방식 개발 문서·CI·수동 배포 워크플로

### 1차 범위 밖 (나중 단계)
- PC 실행기(yt-dlp + ffmpeg → Groq Whisper) 연동 — 7단계
- 분석(주장, 비판적 분석, 숫자 근거 검증) — 8단계
- MP3 업로드 전사 (기존 기능은 7단계에서 PC 실행기와 함께 재연결)
- 화자 분리, 외부 사실 확인, 다중 사용자, 유료 모델

## 3. 제약

1. **무료 유지**
   - `ALLOW_PAID_API=false` 고정. 코드에 유료 모델 ID나 유료 모드 호출 경로를 두지 않는다.
   - Supadata는 항상 `mode=native`를 명시한다. 기본값 `auto`는 자막이 없을 때 AI 전사(분당 2크레딧)로 넘어가므로 금지한다.
   - Gemini 키는 **결제가 연결되지 않은 Google 프로젝트**에서 발급해야 무료 등급으로만 동작한다(사용자 확인 사항).
   - 앱 안에 제공자별 **일일 호출 상한**을 두고, 상한 도달 시 다음 날까지 대기 상태로 둔다.
2. **기존 운영 보존**
   - Worker 이름 `holy-rice-b914`, D1 `youtube-ai-analyzer-private-db`, Access 설정, Secret(`ACCESS_OWNER_EMAIL`, `KEY_ENCRYPTION_KEY_B64` 등)은 그대로 유지한다.
   - D1 기존 테이블(`jobs`, `provider_credentials`, `yta_*` 등)은 수정·삭제하지 않는다. v1은 `v1_` 접두사 새 테이블만 **추가**한다.
   - 기존 암호화된 제공자 키는 그대로 읽어서 쓴다(재등록 불필요가 목표).
3. **보안**: Cloudflare Access JWT 검증, 동일 출처 쓰기 검사, 키는 브라우저·로그·응답에 노출하지 않는다(기존 규칙 유지).
4. **배포는 별도 승인**: 코드 병합과 배포를 분리한다. 배포는 수동 GitHub Actions(Worker 이름 입력 확인)로만 한다.
5. **무료 플랫폼 한도** (2026-11 기준 문서 확인, 착수 시 재확인)
   - Gemini 무료 등급: YouTube 영상 **하루 합계 8시간**, 공개 영상만 가능
   - Supadata 무료: 월 100크레딧, 자막 조회 1회 = 1크레딧
   - Cloudflare Workflows 무료: 인스턴스당 1,024단계, 하루 3,000단계, 상태 보존 3일
   - Groq 무료 한도는 콘솔에서 확인 후 설정값으로 둔다.

## 4. 구조

```
[브라우저 / PWA]
   │  POST /api/v1/jobs {url}
   ▼
[Worker holy-rice-b914]  ── Access JWT 검증 ── 정적 화면(web)
   │  Workflow 인스턴스 시작
   ▼
[Cloudflare Workflow: SummaryJob]   ← 단계마다 저장, 실패 시 자동 재시도
   1. 메타데이터 확인 (영상 ID, 제목, 길이)
   2. 자막/전사 확보  (아래 순서로 시도)
   3. 전사문 정규화·구간 나누기
   4. 구간별 요약 (map)
   5. 전체 요약 + 챕터 생성 (reduce)
   6. 결과 검증 → 저장
   ▼
[D1: v1_jobs, v1_transcripts, v1_summaries, v1_usage]
```

### 4.1 자막/전사 확보 순서

| 순서 | 방법 | 비용 | 비고 |
|---|---|---|---|
| 1 | Supadata `mode=native` (기존 자막) | 1크레딧/영상 | 자막 있는 영상은 가장 빠르고 정확 |
| 2 | Gemini에 YouTube URL 직접 입력, **10분 단위 구간 전사** | 무료(하루 8시간) | 구간 지정(`videoMetadata` 시작/끝)과 저해상도 설정으로 토큰을 줄인다 |
| 3 | PC 실행기 yt-dlp → Groq Whisper | 무료 | 7단계에서 연결. PC가 켜져 있어야 함 |
| 4 | 사용자 SRT/VTT/TXT 업로드 | 무료 | 항상 가능한 대체 경로 |

- 1에서 자막이 없으면 2로 자동으로 넘어간다.
- 2가 실패하면(비공개, 연령 제한, 한도 초과 등) 이유를 화면에 보여 주고 3·4를 안내한다.
- 어느 경로로 전사문을 얻었는지 결과에 기록한다.

### 4.2 요약 방식

- 전사문을 약 15분 단위 구간으로 나누고, 구간마다 요약한다(map).
- 구간 요약을 모아 최종 결과를 만든다(reduce).
  - **핵심 요약**: 5~10개 항목
  - **챕터**: 시작 시각, 제목, 2~3문장 설명. 시작 시각을 누르면 YouTube 해당 위치로 이동한다.
- Gemini **응답 스키마 고정**(JSON schema)으로 형식 오류를 원천적으로 줄인다.
- 검증: 스키마 일치, 챕터 시각이 영상 길이 안에 있고 오름차순인지 확인
  - 실패 시 같은 요청을 **1회만 자동 재시도**하고, 그래도 실패하면 오류 이유와 함께 `FAILED`로 표시한다.
  - 지금 멈춰 있는 `FAILED_UNCERTAIN` 같은 애매한 상태는 두지 않는다.
- 요약 모델: Gemini 무료 Flash 계열(모델 ID는 설정값). Groq 무료 LLM은 대체 요약기로 둔다.

### 4.3 재사용할 기존 코드

| 기존 파일 | 재사용 내용 | 방식 |
|---|---|---|
| `src/access.mjs` | Access JWT 검증 | 가독성 정리 후 이동, 기존 테스트 유지 |
| `src/vault.mjs` | 키 암호화·복호화 | 그대로 사용 (기존 D1 키 호환) |
| `src/core.mjs` | URL→영상 ID, SRT/VTT 파서 | 필요한 함수만 가져와 정리 |
| `src/adapters.mjs` | Supadata/Gemini/Groq 호출 | 새 클라이언트로 다시 작성하며 요청 형식 참고 |
| `src/audio.mjs`, `scripts/local-*` | MP3 프레임 분할, PC 실행기 | 7단계에서 재사용 |
| `web/site/style.css` | 화면 디자인 | 참고해서 새 화면에 적용 |

### 4.4 코드 규칙

- 새 코드는 `src/v1/`, 새 화면은 `web/app/`에 둔다. 기존 코드는 v1 운영 확인 전까지 삭제하지 않는다.
- 일반적인 줄바꿈·들여쓰기. 한 파일 약 400줄 이내, 한 줄 120자 이내.
- 오류 코드는 수십 개 수준으로 제한하고 사용자 메시지와 1:1로 둔다.
- 외부 의존성은 최소화한다(번들러 없이 ESM 유지).

### 4.5 D1 새 테이블 (추가만)

- `v1_jobs`: id, video_id, url, title, duration_s, status, transcript_source, error_code, created_at, updated_at
- `v1_transcripts`: job_id, segments_json(시작·끝·텍스트), language, char_count
- `v1_summaries`: job_id, model, summary_json(핵심 요약·챕터), created_at
- `v1_usage`: date, provider, calls, units — 일일 상한 계산용

### 4.6 문서·운영 (map-bot 방식)

- `AGENTS.md`(모든 AI 공통 규칙), `CLAUDE.md`(진입점), `AI_HANDOFF.md`(현재 상태), `TASKS.md`(남은 일), `ARCHITECTURE.md`
- `.github/workflows/ci.yml`: 비밀값 없이 검사·테스트
- `.github/workflows/deploy.yml`: 수동 실행 + Worker 이름 입력 확인 후 배포
- 기존 `docs/` 검토 기록은 `docs/legacy/`로 옮겨 보존한다.

## 6. 주요 결정과 이유

| 결정 | 이유 |
|---|---|
| 기존 코드 위에 덧붙이지 않고 재구성 | 승인 단계 40종·오류 코드 841종과 압축된 형태의 파일 때문에 수정 비용이 크고, 핵심 흐름이 아직 한 번도 끝까지 완성되지 않음 |
| Workflow 사용 | 긴 영상 처리를 요청 하나 안에서 끝낼 수 없음. 단계별 저장·자동 재시도를 플랫폼이 제공하고 무료 한도로 충분 |
| Gemini 구간 전사 | 서버에서 yt-dlp를 쓸 수 없고 YouTube가 데이터센터 IP를 막는 문제를 피함. 무료 하루 8시간 |
| 응답 스키마 고정 | 기존 `FAILED_UNCERTAIN`의 원인(형식 오류)을 구조적으로 줄임 |
| 사람 승인 대신 자동 상한 | 무료만 쓰므로 과금 위험이 없고, 일일 상한으로 남용을 막으면 충분 |
| 기존 D1에 `v1_` 테이블 추가만 | 기존 데이터·이력 보존, 문제 시 기존 화면으로 되돌리기 쉬움 |

## 7. 위험과 남은 이슈

1. **Gemini 무료 등급의 데이터 사용**: Google 무료 등급은 입력 내용이 제품 개선에 쓰일 수 있다. 공개 영상 요약 용도라 수용 가능하다고 판단했지만 사용자 확인이 필요하다.
2. Gemini가 일부 영상(연령 제한, 지역 제한, 실시간 방송)을 처리하지 못할 수 있다 → 3·4번 경로로 안내.
3. 무료 한도는 제공자가 바꿀 수 있다 → 상한값은 코드가 아니라 설정값으로 두고, 429 응답 시 대기 후 재시도한다.
4. 2시간 영상 전체를 Gemini로 전사하면 하루 8시간 한도 중 2시간을 쓴다. 하루 약 4편이 한계다.
5. Workflow 바인딩 추가는 `wrangler.toml` 변경이 필요하다 → 6단계 배포 승인 때 함께 확인한다.
6. 기존 v0.7 화면에서 만든 보고서를 v1 라이브러리에 보여줄지는 미정이다(기본안: 읽기 전용 "이전 보고서" 탭, 5단계에서 결정).
