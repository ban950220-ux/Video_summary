# Workers Free 한도 대응 설계 (사용자 확인 전)

작성 2026-11-24. 근거: 사용자가 전달한 인계 문서(PORTFLOW 세션 작성, 2026-11-25자)와 Cloudflare 공식 한도 문서(Workers 2026-11-19, Workflows 2026-11-10 수정본).

## 1. 상황
- Cloudflare 계정이 Workers Free다. 한도는 계정 전체에 적용된다.
- 관련 한도(공식 문서 확인):
  - HTTP 요청 1건당 CPU 10ms. 네트워크·D1 대기 시간은 제외.
  - **Workflow 단계 1개당 CPU 10ms.** 요약 작업은 Workflow 단계로 돈다.
  - 요청 1건당 외부 호출 50건, 하루 요청 10만 건, Workflow 단계 1,024개, 인스턴스 상태 100MB, 완료 기록 보관 3일.
  - 초과 시: 가끔 넘는 것은 허용하지만 꾸준히 넘으면 종료한다고만 적혀 있다(오류 1102, 지표 `exceededResources`).
- 인계 문서의 측정값(`holy-rice-b914`, 2026-11-18~24, 465건): CPU P50 3.0ms, P75 9.3ms, P99 98.1ms, 최대 130.9ms. 자원 초과 종료 건수는 적혀 있지 않다.

## 2. 지금까지 확인한 것 (로컬 측정, 운영 측정 아님)
98분 영상의 실제 작업 자료(전사 116KB, 구간 1,226개)로 Node에서 CPU를 쟀다. Workers와 절대값은 다르고 순위만 참고한다.

| 작업 | 반복 시 | 첫 실행 |
|---|---|---|
| 결과 화면 조회 전체(전사 파싱 + 숫자 검증 + 검토 목록 + 응답 만들기) | 5.3ms | — |
| 그중 숫자 검증(`verifySummary`) | 4.5ms | 17.9ms |
| 전사 JSON 파싱 | 0.5ms | 0.6ms |
| 응답 JSON 만들기 | 1.2ms | — |
| 요약 단계(전사 파싱 + 프롬프트, 또는 결과 검증) | 0.9~1.3ms | — |
| 내보내기(Markdown, JSON) | 0.1~0.4ms | — |
| Access 서명 확인 | 0.15ms | — |

- v1 코드에서 가장 무거운 것은 **결과 화면을 열 때마다 다시 하는 숫자 검증**이다.
- 확인하지 못한 것:
  - 운영에서 실제로 10ms를 넘는 경로. 분석 API는 경로별로 나눠 주지 않고, 이 세션에는 분석 조회 권한이 없다.
  - 기존(v0.7) 화면과 그 API의 CPU. 운영 코드라서 고치려면 따로 승인이 필요하다.
  - Workflow 단계의 운영 CPU.

## 3. 목표와 범위
- 목표: 실제 사용 흐름(첫 접속, 목록, 결과 열기, 요약 실행, 내보내기)에서 모든 요청과 Workflow 단계의 CPU가 10ms 미만, `exceededResources` 0건.
- 범위: `src/v1/`, `web/app/`, v1 스크립트·테스트·문서, 측정용 GitHub Actions 워크플로 1개.
- 범위 밖: 운영 코드(`production/dede9fb3/`) 수정, 다른 프로젝트의 Worker·DB, 유료 요금제 전환.
- 제약: 비밀값·계정 ID·전사 원문을 로그와 저장소에 넣지 않는다. Gemini 월 예산 상한을 유지한다.

## 4. 단계
1. **운영 측정 수단 마련**
   - 수동 실행 워크플로 "Measure CPU"를 추가한다. 기존 배포용 Secret으로 분석 API를 조회해 CPU 분위수·최대값·상태별 건수만 출력한다(계정 ID와 원문 응답은 출력하지 않음).
   - 완료 기준: 워크플로가 최근 24시간 값을 출력하고, 테스트가 계정 정보 미출력을 검사한다.
   - 사용자 작업 가능성: 배포용 토큰에 Account Analytics 읽기 권한이 없으면 추가가 필요하다.
2. **경로별 원인 확정**
   - 한 번에 한 가지 흐름만 운영에서 실행하고 15분 구간 값을 읽어 흐름별 CPU를 분리한다(목록, 결과 열기, 내보내기, 요약 1회, 기존 화면).
   - 완료 기준: 흐름별 최대 CPU 표와 10ms 초과 흐름 목록.
3. **초과 흐름 수정** (2단계 결과에 따라 확정. 현재 예상안)
   - 숫자 검증을 조회 때마다 하지 않고, 요약 저장 때 여러 Workflow 단계로 나눠 계산해 저장한다. 조회는 저장본을 읽기만 한다. 저장본이 없는 예전 요약은 한 번 계산해 저장한다.
   - 결과 화면이 전사 전체를 매번 받지 않게 한다(근거 구간만 요청).
   - 완료 기준: 해당 흐름의 운영 CPU 최대값 10ms 미만, 기존 테스트 통과.
4. **Workflow 단계 점검**
   - 요약 1회를 실행해 단계 CPU를 측정한다. 넘는 단계는 더 잘게 나눈다.
   - 완료 기준: 요약 1회 동안 `exceededResources` 0건. Gemini 비용 약 230원 사용.
5. **새 인스턴스 첫 요청 포함 재측정과 보고**
   - 배포 직후와 몇 시간 뒤 첫 접속을 포함해 다시 잰다.
   - 완료 기준: 인계 문서 5절의 기준 충족. 못 줄인 기능은 대안(GitHub Actions로 이전, 기능 축소, 유료 $5)과 함께 보고.

## 5. 미리 알릴 위험
- 기존(v0.7) 화면이 10ms를 넘으면 v1 범위 안에서는 고칠 수 없다. 대안은 첫 화면을 v1로 돌리거나 운영 코드 수정을 승인받는 것이다.
- PC 실행기가 올리는 전사 저장(불확실 표시 계산 포함)과 Gemini 전사 결과 처리도 후보다. 2단계에서 함께 잰다.
- 한도 초과가 "가끔은 허용"이라, 지금 당장 장애가 나는 것은 아니다. 다만 긴 영상에서 요약이 중간에 끊길 수 있다.
